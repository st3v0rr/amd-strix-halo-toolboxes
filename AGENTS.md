# AI Agent Context: AMD Strix Halo Llama.cpp Toolboxes

**Primary Goal:** This fork of [kyuz0/amd-strix-halo-toolboxes](https://github.com/kyuz0/amd-strix-halo-toolboxes) turns the upstream toolboxes — containers you *enter* — into containers that *start a server*, and adds a web interface to run the whole box from a browser: `llama-server` instances, RPC workers and the media API for image and video generation and speech-to-text, plus both model trees. Target hardware is AMD Ryzen AI Max "Strix Halo" (gfx1151) with up to 124 GiB of unified memory.

Upstream's own parts — the interactive toolboxes, the benchmark suite, the GitHub Pages site, the distributed-inference TUI and the GPU workload watcher — are deliberately **not** carried here; they live in the upstream repository.

## Core Technologies
*   **Containers**: Podman (Docker for building) runs every image as a server container; the web interface drives it as a `systemd --user` service. Toolbx and Distrobox belong to upstream's interactive toolboxes, which this fork does not carry.
*   **Inference Engines**: [Llama.cpp](https://github.com/ggerganov/llama.cpp) (`llama-server`, RPC workers) for text; PyTorch + diffusers on ROCm (AMD's released gfx1151 wheels, pinned) for the media API's image and video generation, and transformers on the same torch for its speech-to-text (Whisper, Qwen3-ASR).
*   **Hardware / Drivers**: AMD "Strix Halo" APUs (Gfx1151). The `llama-server` images are built on Fedora 44 against ROCm 10.0 (`rocm-10.0`, `rocm-10.0-strix-llama`) and ROCm 10.1 (`rocm-10.1`) and Vulkan via Mesa RADV (`vulkan-radv`). `vulkan-amdvlk`, `rocm-6.4.4` and `rocm-7.14` are no longer built.

## Repository Structure Overview
*   `/toolboxes_llama_server/`: Dockerfiles for the `llama-server` images (`vulkan-radv`, `rocm-10.0`, `rocm-10.1`, and the experimental `rocm-10.0-strix-llama`). Each is upstream's file with the shell CMD replaced by a server start; `rocm-10.1` has no upstream counterpart and is `rocm-10.0` with only the ROCm version changed — keep the two in step. Also holds the VRAM estimator the web interface runs, and this directory's `Dockerfile.<tag>` names are what the image catalog offers.
*   `/toolboxes_media_api/`: the media API image — a FastAPI service (`src/media_api/`) for Qwen-Image-2512, Qwen-Image-Edit-2511 and MiniMax-H3 on diffusers and for speech-to-text with Whisper large-v3-turbo and Qwen3-ASR (+ forced aligner) on transformers, plus a vanilla-JS playground. Audio uploads are decoded once to 16 kHz mono WAV by the one demuxer their declared type allows; the windowing, timeline and output formats live in `speech.py` without torch, so the mock backend runs them too. Not upstream's: its Dockerfile is ours. Model profiles are data (`src/media_api/data/models.yaml`, revisions pinned); the built-in registry lists only profiles that run — no `unsupported` or `experimental` entries; rejected formats are documented in that directory's README instead. Tests run without a GPU (`MEDIA_BACKEND=mock`); `tests/test_real_adapters.py` checks the loaders against the real checkpoints' key layouts. Run `pytest`, `ruff check`, `ruff format --check` and `mypy` in that directory after changes; the image itself is checked on the Strix Halo box, since no CI runner has the GPU.
*   `/webui/`: Express + React management interface (JWT-protected) for models, containers, images and app updates. Runs as a `systemd --user` service on the box. It manages the media API as a container role of its own (`server/src/media/`; started from the Servers page, curated models on page `/media-models`): settings in `media-api.json`, its model tree the general setting `mediaModelsDir` (default `~/media-api-models`; a stored `comfyModelsDir` from older configs is carried over) unless `media-api.json` names its own, key and session secret as 0600 files mounted read-only and never returned by any route, the model inventory, fetches and removals through the image's `media-api-models check|fetch|remove --json`. Also an MCP server at `/mcp` (bearer token): its tools in `server/src/mcp/tools.js` call the REST API over loopback, so a new endpoint an agent should reach needs a tool there too. Node backend, no native npm modules by design, so `npm ci` stays reliable across Node upgrades.
*   `run-llama-server.sh`: starts one server from the command line. Kept above all because `dev/parity` runs *this* script against a fake podman and diffs its arguments against `argv.js` — delete it and that check dies.
*   `.github/workflows/`: GitHub Actions. The `llama-server` images rebuild when `llama.cpp` master moves (poller → build); `rocm-10.0-strix-llama` has its own poller on its two source branches, since it builds from neither llama.cpp nor a pinned revision. The media API build is manual, since it pulls a full ROCm torch (tests, then build and push; the image is checked on the box, not on the GPU-less runner). After each `llama-server` build, `prune-old-toolboxes.yml` keeps only the newest tags per backend on Docker Hub (can also be started by hand).

## Critical Technical Quirks (Important for Development)
*   **Flash Attention & no-mmap**: Running `llama-server` or `llama-cli` on Strix Halo *requires* `-fa 1` (flash attention) and `--no-mmap` to avoid memory fragmentation and crashes.
*   **Kernel memory params**: The optimal Strix Halo host configuration relies on custom boot parameters (`iommu=pt amdgpu.gttsize=126976 ttm.pages_limit=32505856`) to allocate unified RAM to the iGPU.
*   **Kernel Bugs**: Avoid kernels older than 6.18.4, and the specifically broken `linux-firmware-20251125`.

## General Instructions for Coding Agents
1.  **Container Builds**: When modifying `Dockerfile.*` files inside `/toolboxes_llama_server`, ensure the build output remains lean and only necessary runtime dependencies and Llama.cpp binaries are carried over. Those files are upstream's with two changed blocks: the shell CMD replaced by a `llama-server` start, and the llama.cpp patch step, which applies `llama-grammar.patch` (all images) and, in the ROCm images, our `llama-cpp-25992-rocm-host-buffer.patch` (temporary workaround for llama.cpp #25992) only after a check, and fails the build when a patch no longer applies and is not already upstream. Keep the diff against upstream to those two blocks, and drop the #25992 patch once llama.cpp carries the fix.
2.  **Documentation Synchronization**: If adding a new backend or feature, ensure `README.md` is updated simultaneously.
3.  **Device access**: Anything touching the GPU needs `/dev/dri` and `/dev/kfd` plus the `video` and `render` groups.
4.  **Media API secrets**: never weaken fail-closed startup (no key → exit 2), never log or echo the key, and never let a request trigger a Hugging Face download unless `MEDIA_ALLOW_DOWNLOADS=1`.
5.  **WebUI parity**: `webui/server/src/podman/argv.js` reproduces `run-llama-server.sh` exactly. If you change either one, run `npm run test:parity` in `webui/` — it diffs our argv against what the real script executes. Never use `shell: true` there; all subprocesses go through `webui/server/src/lib/exec.js` with argv arrays (enforced by ESLint).
6.  **Media API in the WebUI**: `buildMediaRunArgv` is held to the hardened `podman run` in `toolboxes_media_api/README.md` by `server/test/media-parity.test.js`, and the environment it sets is loaded by the service's own `config.py` in `npm run test:parity`. Changing the README's command, a `MEDIA_*` variable or a limit range on either side means running both. The `--json` output of `media-api-models` is read by `webui/server/src/media/`; change its shape only together with that side. No route or MCP tool may return a media secret.
